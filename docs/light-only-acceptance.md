## Compatible avatar identity

The compatibility locator accepts exactly one of the existing button named `User menu` or the future static element with `role="img"` and accessible name `Local workspace avatar`. It requires one match, visible text `L`, and retained rendered geometry and styling. It does not open or make an optional observation of a missing control. Feature 68 should expose the latter static identity and separately prove that no appearance action or empty interactive menu remains.

The existing `theme-observation.ts` helper is unchanged. These revised files remove its calls because the compatibility contract no longer requires a theme control.

## Feature and owner evidence boundaries

Feature 68 owns new failing checks for saved `loop.theme=dark` being overridden before the first populated app/preview mount, light startup and subsequent reload/navigation despite historical preferences and dark system preference, and the absence of theme-switch actions and an empty interactive menu. Compatibility startup states do not substitute for those proofs.

The owner runs the named browser diagnostics against the old light baseline, obtains an independent equivalence/coverage review of the complete test inventory, freezes that inventory, and runs the existing full maintenance verifier. Exact-source final review, verified integration into the reserved requirement branch and native maintenance recording remain required. No gate, verification manifest, CI control, retry, skip, execution budget or product source is changed by this maintenance revision.
