# Browsing requirement delivery

The left primary toolbar has one fixed **Repositories** destination. Initial loading opens the repository directory in main without selecting a repository or moving focus. The directory lists actual enrolled repositories in registry order. Selecting one opens only its **Requirements**. The upper page toolbar identifies the selected repository by name, ID and path alongside **Requirements**, **Repo harness** and **Unassigned**. Returning through **Repositories** clears the inspection scope; the next selection starts in Requirements. The list shows ten requirements per page, ordered by creation time and then identity, newest first. Select a title to inspect the original business goal, conversation provenance, owned child issues, and delivery progress. The child collection includes only issues with both the exact repository and requirement IDs. It uses the shared issue search, status/label filters, sorting and ten-row pagination; label options and counts derive from this owned collection. Each child retains its issue status and recorded merge state. **Reset filters** keeps the selected repository and requirement. Opening child diagnostics retains the requirement context; closing the dialog restores focus to its opener.

Recorded status, child integration, whole-goal acceptance, and final delivery are separate observations. Acceptance requires the latest owned whole-goal verification job to be completed with its exact matching passed, completed run. A historical pass or a Done label cannot replace that evidence. Final delivery also requires at least one child and recorded merges for every child. A requirement's own publication snapshot determines its GitHub enrollment; GitHub delivery additionally requires that snapshot to record merged publication. A requirement without a publication snapshot remains local-only even if its repository is later enrolled for GitHub delivery. Local-only requirements say so explicitly.

Current blockers reflect the latest owned stage and child attempts, excluding recovered failures. A publication reason is current only while publication is blocked. Use the stage-run selector to inspect historical reports and their manifest-listed evidence through the existing readers, including requirements without children. Historical reports retain their own results without changing current acceptance or delivery.

Successful same-scope background refresh retains the current page, selection, and focus. If refresh moves a focused requirement opener off the current page, focus moves to the retained selected inspection heading. Other focused controls retain focus. The directory upper toolbar provides **Refresh repositories** to reload repository and child metadata and **Retry repositories** after a registry failure. Pending or failed registry reads hide stale directory records; loading, failure and empty states appear in main. A removed selected repository or failed registry read returns to the directory without selecting a replacement. Report and evidence errors have their own read retry controls. Switching repositories clears requirement selection and pending report readers. Selecting a different requirement clears local child filters/pages and obsolete issue/report inspection; same-scope background refresh retains valid selection, filters, page and focus. Removed ownership cannot leave an issue report selected. This subview offers inspection only and sends no execution or mutation requests.
