# Adaptive serial execution contract

Current profile: [code-only verification](code-only-verification.md) supersedes earlier browser-specific examples. Four code gates, named Node proofs, frozen inventory and independent reviews remain mandatory; browser obligations and execution are retired.
This separately reviewed acceptance-contract revision stages the authorized four-stage optimization. It becomes active only after the owner integrates the implementation and the protected `factory/execution-policy.json` opts the enrolled repository into `adaptive-v2`. Repositories without policy and version-one tasks retain the existing workflow. Unknown or malformed policy fails closed.

## Behavior coverage and roles

Every acceptance ID maps to meaningful named named Node checks under the code-only profile. Empty, unknown, duplicate and unsafe coverage is rejected. A small requirement normally has one independently verifiable issue. Split work for meaningful dependencies or separate control ownership, not to fill a fixed slice count.

A version-two plan declares `coverage.mode` and its reason. `reuse` selects only existing baseline tests, including their frozen helper inventory. The controller runs actual named proofs and records a distinct baseline coverage receipt bound to the plan, criteria, source, controls and environment. This receipt is an owner admission record, never a fabricated independent acceptance review. Passing old checks do not prove a new feature: implementation still runs and final independent review assesses the goal and coverage relevance. A coverage gap discovered in review enters the existing independently approved regression workflow.

`extend` retains the tests role, expected assertion failures, independent acceptance coverage review and inventory freezing before implementation. Test authors add missing behavior checks at the cheapest meaningful layer. Ordinary feature tasks should not duplicate markup shape, historical issue IDs, or established enforcement owned by the controller unless the change affects that invariant. Harness changes retain focused deterministic regression checks for changed controls. Existing baseline and accepted bytes remain protected during implementation. New permanent defect checks require a confirmed significant OR recurring project defect and worthwhile deterministic prevention that outweighs authoring, maintenance and execution cost. Minor one-off findings may use existing meaningful coverage plus repair and independent review with `needsRegression: false`. New business behavior still needs meaningful acceptance; significant harness safety changes retain targeted regressions. Record the judgment in existing plan defaults and review/coverage summaries, without another role, registry, schema or gate.

## Verification and handoff

Adaptive integrated tasks use focused named development checks as diagnostics, then one fresh complete verifier on the final integrated candidate and independent source review before advancing the target. Diagnostics cannot substitute for the full verifier. Tasks without an integration target still require complete candidate verification and independent review. Target movement, changed controls or changed source invalidate reuse and require revalidation.

Role handoffs retain the original goal, approved defaults, relevant path and check indexes, complete feedback, and exact evidence paths and hashes. Summaries do not replace underlying source or machine evidence. Reviewers independently inspect source and reports; workers cannot claim completion.

## Recovery and requirement delivery

Failures distinguish product, test-contract, positively identified infrastructure, and unknown causes. Only a recognized structured spawn failure from a settled owned process permits one persistent same-source verifier retry. Assertions, unknown timeouts, cancellation, ownership faults and missing or malformed reports do not grant this retry. Keep original failures, cumulative elapsed budgets, retry counts, accepted checkpoints and ownership lineage across runs.

Whole-requirement verification may reuse an actual merged child full run only when requirement membership, target commit, source, runtime, engine, dependency/control/contract identities, machine report hashes and required named cases still match, with approved integrated source review. Otherwise run fresh verification. Record original run IDs and timestamps explicitly. Never manufacture a fresh successful execution.

Keep latest-attempt admission for every child, then select a candidate certificate by the current target branch, commit and source. Job admission numbers do not order child integrations; an earlier maintenance job without a certificate must not mask a later matching feature proof. All existing evidence validation and multi-child whole-goal review requirements still apply.

Review receipts and certificate inspection hash the same parsed verification contract: schema version and required Node file-title identities. `browserChecks` is an empty compatibility field; all acceptance mappings remain bound by the complete plan hash. Original contract artifact bytes remain in the certificate proofs. Changing a plan mapping, required case or machine report still invalidates reuse. `tests/verification-reuse-node-mapping.test.ts` exercises actual version-two integration, certificate capture, original-report reuse and rejection of changed mappings and evidence.

A combined independent review may cover integrated code and the original whole goal only for the sole immutable child, binding the exact requirement ID, original goal and acceptance identity. Generic code review and multi-issue requirements do not satisfy this exception. GitHub publication still requires original-goal acceptance, exact-head CI, confirmed merge and local synchronization.

Existing JSON and Markdown delivery reports record the selected route and reason, actual agent invocations, authoring and review durations, verifier executions, retries, evidence reuse and limitations. Controlled fixture measurements describe orchestration only; they cannot promise model latency or production task completion time.

Owner-resume accepts explicit 0/0 remaining-budget continuation without adding grants or resetting canonical task limits, counters or time. Read-only task-bound admission accounts for crashed reservations and requires implementation/time capacity, plus acceptance capacity when no valid accepted checkpoint exists. Invalid claimed accepted proof is rejected before journaling or enqueueing. Original authority and engine identities, native selected-job dispatch, execution-free exact replay, fresh complete verification and independent integration remain required. Focused-failure triage may approve scoped harness source compatibility repair under the actual authority while preserving accepted diagnostics; uncertain or actual test-contract faults remain blocked for maintenance. Dependent maintenance activates the verified integrated predecessor only after quiescent handoff. The [three pending business observations](stability-observation.md) add no execution path or completion gate.
