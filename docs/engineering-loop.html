THE OBJECTS & THE ROLES

先分清对象，再分清角色

数据库里的任务对象，与执行它们的 agent／控制程序是两套概念。理解这个区别，才能读懂一个 issue 为什么会有多次运行和多份报告。

对象表示什么关键点
Repo登记的代码仓库路径＋targetBranch。跟踪任何 repo 不代表能直接执行任意技术栈。
Requirement完整业务目标保存最初想实现什么；全部子项合入后仍要整体验收。
Submission整份不可变入口计划submissionId、planHash、对话来源、issue keys 和依赖映射。
Issue一块可验证的交付归属、验收、依赖、changeKind。也支持没有 requirement 的独立 issue。
Task / Plan单个 issue 的执行契约／技术映射Task 固定目标、scope、预算；Plan 把验收映射到具体 file＋test title。
Job持久化排队项plan_review / issue / requirement_verify / maintenance 等类型。
Run某个 job 的这一次执行唯一 runId；包含开始结束、证据路径和 passed / merged / blocked 结果。
Receipt可复核的凭证把批准／合入结果与精确源码、计划、验收和证据绑定。

两个“规划”解决不同问题

整份需求 → 多个 issues

会话 agent 拆业务交付、依赖和每个 issue 的验收。提交到平台后独立审查这份拆分的覆盖度。

一个 issue → 技术切片与具名检查

plan agent 研究代码，决定这条 issue 由哪些切片实现，并把验收映射到具体测试文件与标题。

角色主要判断职责边界
会话 agent理解业务、整份拆分和默认值提交整份计划；不与已提交任务抢着执行。
plan agent单个 issue 的技术与测试映射只读；不能擅自修改原始验收。
tests agent补初始测试或漏测回归初始允许保留原字节后追加；regression-tests 只允许新文件。
acceptance reviewer审查测试是不是有效的尺子只读；看具体断言、边界和实际红证明。
implement / repair agent实现或按失败证据修复写受限工作区；不能改已冻结检查或自行合入。
code reviewer完整验证后审查真实代码普通自动合入任务只做一次权威 integrated-code 评审。
requirement reviewer审查初始拆分或最终整体交付对照原业务目标，而非仅检查子任务数量。
controller / verifier状态推进、强约束、实际运行、报告、合入普通程序；只有它们有权依据证据决定交付。
“独立角色”怎样落到代码上？每个阶段用不同 prompt／schema 启动新的 codex exec --ephemeral 会话。独立评审意味着不沿用实现者的同一段执行会话；不代表不同模型必然不会犯同一种错。确定性测试与程序边界仍然必要。

放行条件目标实例正确，计划合法，事务完成；回执只表示提交成功。

  submitPlan(input: unknown): SubmissionReceipt & { replayed: boolean } {
    const plan = parseSubmission(input);
    const serialized = JSON.stringify(plan);
    const planHash = createHash('sha256').update(serialized).digest('hex');
    return this.transaction(() => {
      const existing = this.submission(plan.submissionId);
      if (existing) {
        if (existing.planHash !== planHash) throw new ConflictError('Submission ID already belongs to a different immutable plan.');
        return { ...this.submissionReceipt(existing.id)!, replayed: true };
      }
      const requirement = this.addRequirement({ repoId: plan.repoId, ...plan.requirement });
      const created = this.createSlices(requirement, plan.issues);
      const issueIds = Object.fromEntries([...created].map(([key, issue]) => [key, issue.id]));
      this.database.prepare('INSERT INTO plan_submissions (id, requirement_id, plan_hash, plan, issue_ids, created_at) VALUES (?, ?, ?, ?, ?, ?)').run(plan.submissionId, requirement.id, planHash, serialized, JSON.stringify(issueIds), new Date().toISOString());
      this.startRequirement(requirement.id);
      return { ...this.submissionReceipt(plan.submissionId)!, replayed: false };

程序强约束

串行领取一个依赖已满足的 job

负责：daemon ＋ SQLite claim

输入
持久化的 queued jobs、依赖图、历史 merge receipts。
产出
job=running、一个新的 runId、冻结的 job payload 与专属证据目录。

这一步在做什么

daemon 循环调用 SerialQueue.processNext。队列目前跨已登记仓库串行工作，一次只推进一个 job。Issue、计划评审和整需求验收都是不同 job 类型。

代码怎样实现

数据库事务中的 claim 先检查全局是否有 running job，再找第一个可运行任务。依赖检查查询 work_runs.status=merged，不信任手动设置的 Done。claim 同时更新 job、插入 run、记录开始时间和证据路径。daemon 的 queue lease 进一步防止两个 worker 进程占用同一数据库队列。

为什么需要它

Issue 是“要完成什么”；Job 是“等待执行的一项工作”；Run 是“这一次具体尝试”。把它们分开，重试才不会覆盖历史，也不会因为 UI 状态改变而假装依赖已经交付。

放行条件没有其他运行中 job，且每个依赖都有真实 merged run。

WHEN THINGS GO WRONG

失败会走哪条分支？

“失败”并不是统一的重新开始。已有覆盖的代码错误、缺少测试的缺陷、进程中断和完整性错误，有不同的处理方式。

新补上的最小回归闭环

独立代码评审：needsRegression = true → tests 角色：只创建新的 scoped 测试文件 → controller：对当前缺陷版本跑具名红证明 → acceptance reviewer：批准断言与覆盖 → controller：冻结新测试，加入有效验证契约 → repair：修产品代码，保留已冻结检查 → 候选完整验证 → 集成完整验证＋代码评审 → 合入 → 以后 npm run verify 自动再执行这些新文件
这条分支没有新增一套缺陷登记系统。缺陷由真实 code-review findings 提出；新测试、红证明、coverage receipt 和冻结哈希已经形成必要证据。测试角色新增的文件必须全部申报，已有实现和旧测试都不能改。即使新测试“已经绿了”，也不能冒充这条分支要求的红证明。

有测试的错误

已有 trim 测试失败 → repair 恢复 trim → 跑原检查与完整回归。无需额外补一个等价测试。

测试没有覆盖的缺陷

全部测试通过，reviewer 却确认刷新会丢焦点 → 先写会失败的回归 → 批准并冻结 → 再修实现。

真实例子：后台刷新后关闭弹窗丢失焦点

  1. 问题触发：打开 issue 弹窗后，后台 job 状态变化触发 issue 列表刷新。
  2. 旧实现刷新时卸载原列表按钮；Modal 记住的 opener DOM 引用失效，关闭后焦点无法回到原按钮。
  3. 正式用例持有原按钮的 ElementHandle，延迟真实 issue 刷新请求，断言刷新中原元素仍然 isConnected。
  4. 随后分别模拟刷新成功／失败，关闭弹窗并断言原入口获得焦点；覆盖标题／编号两个入口，共四种组合。
  5. 相同测试在缺陷基线 970c406 上发生预期断言失败，在已修复版本上通过；最终以 acceptance/refresh-focus.spec.ts 进入常规测试发现。

这次把已经修复的历史缺陷升级成正式回归，因此红证明使用明确的旧基线。将来 controller 现场补漏测时，红证明必须针对 reviewer 指出的同一候选源码。

候选验证

在 issue 工作树回答：这份候选实现单独满足标准了吗？

集成验证

在最新目标上应用 patch 后回答：与现有代码组合后仍满足标准吗？

整需求验收另有一个问题。所有子 issues 合入之后，最终版本是否实现了最初的完整业务目标？因此会再次做完整机器验证和对照原目标的整体评审。它不等于把若干子 issue 的通过数量相加。

通过条件比一句 “passed” 更严格

  • 五个 gate 的进程结果都必须成功；超时、取消、失败会中止。
  • Node 的最终机器报告必须完整，失败、取消、skip、todo 为零；controller 计划的具名 Node case 必须真实出现。
  • 浏览器机器报告必须包含实际执行结果、正确数量和所有必需用例；不能有 skip、flaky、报告错误或失败重试结果。
  • 有效契约包含既有强制项与本任务新增的具名检查；实现者不能删掉它们。
  • 源码 inventory 与 verification contract 在验证期间保持一致；之后代码变了，旧通过记录不再证明新代码。
  • 独立 reviewer 同时看真实 diff、源码与这些证据，不仅看 worker 的总结。

为什么 SHA-256 很重要，又为什么它还不够？

源码快照把每个 tracked／非 ignored 文件的内容变成摘要，再汇总成 sourceHash。报告、评审凭证和最终提交因此能指向同一份源码。生成物、依赖、.runs、.data 和 .env 不参与这个 inventory。哈希证明“对应的代码没有被偷换”，业务是否正确仍取决于有意义的测试与审查。

RETRY WITH MEMORY, NOT A CLEAN SLATE

续跑保留什么，重新检查什么？

续跑目标是复用可信的计划、测试和实现草稿，不继承旧的“已经通过”结论。是否能复用由 controller 校验，worker 不能自己声明从某阶段恢复。

Checkpoint 里有什么

  • 基线 commit／tree、可重建的二进制 patch。
  • 目标、验收、scope、预算、运行环境／harness 身份。
  • 计划、已批准测试的哈希、红证明及其文件哈希。
  • 独立 coverage receipt，必要的 pending／accepted regression 信息。

恢复时必须重新成立什么

  • 前任 controller 与所有继承的 owned 进程组已结束。
  • 目标、标准、原测试、lockfile、runtime、harness 和证明一致。
  • Patch 能重建精确源码，已批准测试未被改写。
  • 恢复后重新跑完整验证与权威代码评审。

两个回归 checkpoint 状态

Pending：已发现漏测，测试还没批准

保留“有缺陷的已评审候选＋待补测请求”。未批准的新测试草稿只保留作证据，不会因中断恢复变成已验收。续跑重新生成、跑红证明并独立评审。

Accepted：新测试已批准并冻结

保留新具名检查、文件哈希、红日志／机器报告及批准凭证。续跑恢复为 frozen checks，继续 repair；不必假装补测从未发生。

刚补上的完整性保护删除 pendingRegression 或 regressions 字段不能让续跑忘掉补测要求。Loader 检查孤立的 needsRegression 评审凭证、coverage receipt 和红证明；元数据缺失或证据被改，会拒绝复用并记录原因。身份失配通常重新规划；仍然活着的旧进程必须先由 owner 处理。

预算跨 run 累计

3 次
acceptance 尝试上限

初始测试评审与后续补漏测共享这笔预算，不是每次 Retry 又送三次。

3 次
implementation 尝试上限

实现与修复消耗独立的 implementation 次数；不是整个流程只允许三个 agent 调用。

10 分钟 / 1 小时
普通 issue 的单 agent 阶段 / 活跃执行总上限

每个阶段取自己的上限和总剩余时间的较小值；排队空闲不算活跃执行。

3 分钟 / 10 分钟
完整 verifier 单 gate / 总默认上限

初始 Node red 单项 30 秒；补回归 Node 30 秒、browser 90 秒。整需求 planner/reviewer 默认单次 5 分钟，格式修复最多再试一次。

预算持久化在 owner 的账本中。硬崩溃时保守计入当前阶段预留时间；旧进程、旧 run 与前任 lineage 都要检查。超时清理针对确切 owned PID／进程组；无法确认安全时保留工作树，不能按进程名称随便 kill，也不能删活锁来绕过。

READ A DELIVERY WITHOUT OPENING EVERY TRACE

先读报告，再按问题钻到证据

  1. 读目标与结果

    Issue 详情 → 当前交付：完成了什么、变了哪些文件、还有什么 blocker。

  2. 核对通过与合入

    看 gate／用例结果、独立评审是否批准、sourceHash、integration commit。别只看 issue 状态或 worker 自述。

  3. 有疑点再看阶段记录

    测试缺覆盖看 red 与 acceptance review；代码疑问看 diff 和 code review；长耗时看 phases；续跑疑问看 checkpoint 与 budget。

  4. 最后才打开低层调试材料

    定位浏览器动作／DOM／网络时再打开失败 trace。成功测试不保留全量 trace，日常审查用摘要与文本证据。

.data/issues.sqlite 应用元数据：repo / requirement / issue / job / run .data/evidence/<run-id>/ 每次执行的持久证据与交付 ├─ task.json / plan.json / state.json ├─ phase-*/ agent 输入／输出与事件 ├─ verification-*/ gate 及机器报告 ├─ review-receipt-*.json 审查凭证 ├─ checkpoint.json / .patch 恢复所需材料 ├─ integration.json 实际合入凭证 └─ delivery.json / delivery.md 人读摘要＋manifest .runs/ 验证指针、直接 verify 和临时运行资料 └─ latest.json 指向最新 summary；实际目录可以在别处
证据记录什么怎么读
task.json / job.json冻结的目标、scope、验收和调度上下文理解这次究竟被授权做什么。
plan.jsonIssue 技术计划和 file＋title 测试映射知道每条验收由什么检查证明。
state.json阶段、尝试、当前原因、预算和恢复信息定位在哪一步失败；不要只看最后一句 worker 总结。
phase-*/prompt.txt / response.json / events.log每个 agent 的输入、结构化输出和详细事件追踪推理上下文和真实工具过程；日志不等于批准。
red-*.jsonl / regression-red-*.json(l)初始 Node 或补漏测的具名红证明确认测试能检出缺陷，而非环境没装好。
review-receipt-*.json源码绑定的覆盖／代码评审记录确认评审目的、批准结果和对应的标准／源码。
verification-*/summary.json ＋ 两类机器报告具体 gate、数量、用例和 sourceHash需要同时看完整 summary 与真实执行报告。
checkpoint.json / checkpoint.patch可信可重建的已批准状态和二进制补丁检查复用了什么、为何失效、是否丢失回归记录。
integration*.json真实分支、before、commit、tree证明结果确实进入指定目标，而非只得到 ready。
delivery.json / delivery.md目标、变更、结果、评审、合入、manifest适合先读的人类交付摘要。

队列会在安全确认后清理候选／集成工作树，但保留证据。.runs 和 .data/evidence 不同：清空前者不会自动删除后者，也不会等于清空 issue 历史。

WHAT THIS LOOP CURRENTLY DOES AND DOESN’T GUARANTEE

边界，决定怎样正确使用它

已经实现应怎样理解
串行自治开发与本地验证合入普通 feature 可以无需逐项人工审批；事后抽查可选。
维护 lane 与普通 feature lane 分离新增业务检查通常跟随 feature；改既有标准／harness 要独立维护 issue。
Owner 维护证据录入record-maintenance 验证真实 commit、机器结果、独立审查及精确 issue 契约；不是手动打 Done。
已登记 repo＋Node/Playwright 执行 profile能跟踪多仓库，但执行其他语言栈需要额外受审的 harness 适配。
角色分工与独立新会话角色是阶段职责，不代表同一时刻并行常驻的多个 agent。
Controller 生成交付报告当前不存在单独的 LLM 报告 worker；程序汇总真实 owner 记录。
有界自动修复与可信恢复普通 Blocked 工作需要原因处理／授权重试，重放提交不会自动重启它。
本地 merge 与 GitHub 发布分离平台不自动 push、创建 PR 或合并远程 PR；这些是另行授权的动作。

AGENTS.md、harness 和 CI 分别管什么？

AGENTS.md 与阶段 prompts

告诉 agent 目标、职责、语言、禁止项和操作约定。文本会影响行为，但单靠文本不能保证过程不越界。

Harness 的确定性代码

Schema、事务、受保护文件、源码哈希、报告解析、ownership、预算和有条件合入，给“是否接受本次结果”提供实际规则。

GitHub CI 可以在 push／PR 事件中自动运行同一套 npm run verify，提供团队共享的运行入口和结果；配置分支保护后还能作为远程合并门槛。当前源码快照的 .github 没有 Actions workflows。本地 loop 的完成是已登记目标的验证合入；GitHub PR 发布／合并不在自动完成条件内。

自动化不等于保证没有未知缺陷。测试和评审能拦住它们所覆盖、所识别的问题。普通实现者与评审者共享主机和 Git／依赖，当前属于合作型本地所有权协议，不是对恶意代码的强隔离。缺少确定性覆盖的已确认问题，应进入补回归闭环；任意故障自动自愈、任意语言仓库执行、并行队列都不是这里已实现的承诺。
