# UI ownership and visual iteration

The application uses React and plain CSS. Start the existing development server with `npm run dev`. Open `/` for the application or `/__ui/components` on that same frontend origin for the component preview. The preview has static samples and local state; it does not mount application reads, polling, reports, evidence loaders or mutation paths. It works without a backend. Its dynamic modules and stylesheet are gated by `import.meta.env.DEV` in the browser entry and are excluded from production output.

Existing direct imports such as `App`, `IssueRow`, `DeliveryView` and `workbench-state` continue to support Node static rendering. Feature modules, components and shared hooks do not import CSS or perform browser initialization at module evaluation.

## Choosing the change location

Change theme tokens for a shared color, type, radius or spacing decision. Colors are named by purpose, including distinct status, evidence, warning, source and navigation treatments. The size scales support the reference hierarchy; semantic aliases such as `--radius-control`, `--space-panel-padding` and `--font-size-control` express common roles. Both themes resolve every feature alias through the neutral palette or a semantic status color; feature files must not embed a dark-only color.

Change a shared component for behavior or markup used by several real screens, and `components/primitives.css` for its shared appearance and responsive sizing. Button preserves native attributes and refs, and its loading state disables activation and exposes `aria-busy`. Badge preserves a native span and accepts the existing status class hooks. EmptyState owns the common message frame. Pagination owns the exact range and boundary controls; Issues, Requirements and the preview supply their own collection and page state. Modal preserves native dialog semantics, neutral initial focus, trapped bidirectional Tab navigation, Escape dismissal and return to its connected opener. Focus outlines are enabled by intentional Tab input through the shared focus-intent hook and styled by `theme/base.css`.

Change feature markup and the stylesheet beside it for screen-specific layout, including its media queries. Shared list frames, pagination and identifiers keep their historical issue-prefixed class names in `components/primitives.css` because Requirements also uses them. Mixed inspection rules used across cards, diagnostics and reports remain in the shared inspection stylesheets. Keep component primitives independent of backend reads. Keep workspace navigation presentation in the layout and navigation decisions in App. `useWorkbenchData` retains the existing abort signals, job-change refresh trigger, two-second metadata polling, retry behavior and previously loaded issues. `useIssueCollection` owns repository scoping, filter/search/sort, page resets, clamping and list scroll reset. Requirements retain their own selection and focus recovery when refreshed rows move across pages.

Production CSS stays centrally loaded through `styles.css`; components and feature modules never import CSS. Its import order is part of the cascade: tokens and document defaults precede shared primitives and inspection basics, followed by workspace, Issues, delivery basics, Requirements, shared inspection refinements, issue diagnostics, report refinements, shared inspection responsive overrides and Repo harness. The separate refinement files preserve later overrides without increasing specificity or adding cascade layers. In particular, the shared mobile metadata/evidence padding follows both feature definitions; report typography follows common inspection typography. Within `workspace.css`, later breadcrumb sizing and mobile repository navigation remain after the earlier shell rules, and the mobile persistence positioning retains its original overrides. Preserve these relationships when restyling an owner, and review selector/declaration equivalence and cascade winners when moving rules. Retained legacy selectors remain with their presentation owner. Do not introduce CSS imports into compatibility entry points. Keep preview styles and fixtures behind the development gate.

## Preview and verification

The preview displays normal, disabled, loading, error, empty and long-content samples using the same production primitives. Activate the local action, open the modal, traverse with Tab and Shift+Tab, dismiss with Escape or Close, and page through the finite sample collection. Inspect at desktop width and at 390px; long identifiers must wrap without page clipping or horizontal overflow.

Run `npm run typecheck`, the relevant existing Node checks and the frozen production browser checks for the affected behavior. The accepted `tests/ui-preview-build.test.ts` inspects actual production artifacts and included modules; `acceptance/ui-components.spec.ts` observes API isolation through entry, interactions, polling intervals and cleanup, modal focus return, pagination and narrow layouts. Preserve all existing acceptance assertions and quality controls. The controller still owns final full verification, independent source review, integration, exact-head GitHub CI and publication. A worker's focused checks do not establish delivery.

## Theme preference and interaction

The application and development preview each expose the same native button with switch semantics and the accessible name **Dark mode**. Its checked state and visible On/Off text describe the selected mode. Pointer activation, Space and Enter use ordinary button behavior. Intentional Tab focus keeps the existing neutral outline; pointer, passive refresh and modal entry keep their existing focus behavior.

Light is the default regardless of the operating system preference. `main.tsx` calls `initializeTheme` before creating or mounting either React entry. The same-origin `loop.theme` localStorage key accepts only exact `light` and `dark` values. Missing, malformed or unreadable storage starts in light. Switching applies the root theme immediately and then attempts persistence; a denied write leaves local switching usable. The document theme-color metadata follows the mode. Reloads and navigation between app and preview use the same saved preference. No API calls or application mutations are part of theme handling.

ThemeSwitch owns only its appearance state. It does not key or remount the workspace, selected requirement, issue filters/pages, reports, dialogs or harness disclosures. Reusable components and preference modules perform no browser work at module evaluation and remain importable for Node rendering. Styles and initialization stay in the browser entry; the preview remains gated out of production builds. The controller's frozen theme cases exercise first-mount resolution, safe storage fallback, accessible persistence, preserved browsing state and representative desktop/390px rendering in both modes. Final integrated verification and independent rendered/source review remain controller responsibilities.
