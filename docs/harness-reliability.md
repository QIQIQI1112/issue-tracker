# Change ownership, review, and recovery

Current profile: [code-only verification](code-only-verification.md) supersedes earlier browser-specific examples. Four code gates, named Node proofs, frozen inventory and independent reviews remain mandatory; browser obligations and execution are retired.
Requirement planning and review retain each invocation's complete evidence string as `evidence.txt`, including response repair attempts. Prompts identify its absolute path, UTF-8 byte count and SHA-256. Evidence up to 8 KiB also remains inline; larger inputs are read through the retained file and compact `context-index.json`. Role context preserves the original goal, exact source, relevant paths, decisions, full feedback bytes and owner evidence hashes. Indexed evidence remains authoritative over worker narrative. Reviewers inspect complete retained evidence, actual source and underlying machine reports rather than approve from summaries. No evidence is truncated, and review schemas, sandbox, deadlines, retry counts and approval gates remain unchanged. Failed invocations retain their evidence for diagnosis.

## Plan changes by responsibility

Keep new behavior checks in their feature issue. First identify changed behavior, its impact, and named existing coverage. Add checks only for uncovered risks, using Node computations, API/storage integration or owned process outcomes. Ordinary feature tasks do not duplicate unchanged controller enforcement; changed harness invariants still need targeted deterministic regressions. The tests worker adds necessary checks; an independent acceptance reviewer evaluates the extension before implementation. A new test is not automatically a new issue. Small cohesive requirements default to one issue; separate delivery, real dependencies or owner-maintenance boundaries justify splitting.

Create a separate `acceptance_contract` issue when changing an existing required assertion, required case, verification gate, or acceptance criterion. Create a separate `harness` issue when changing the controller, verifier, review policy, recovery, budgets, or protected workbench controls. Declare dependencies explicitly. Version-two conversation plans accept `changeKind`; version-one plans retain their original canonical identity. A classification never expands a worker's write permissions.

The ordinary queue leaves maintenance jobs awaiting owner verification. Maintenance is implemented in an isolated owner worktree with its own failing checks, full verification, independent review, and verified local integration. The owner recorder requires actual machine reports for the exact committed source and independent approval covering the exact issue goal and acceptance contract. A generic approval or an old passing build cannot complete unrelated work. Owner maintenance is a cooperative local protocol, not a sandbox for hostile maintainers.

## Review the right evidence at each stage

The owner policy `factory/execution-policy.json` selects `{ "schemaVersion": 1, "mode": "adaptive-v2" }` for newly dispatched queue tasks. A missing policy retains `legacy-v1`; malformed policy blocks instead of silently changing execution. Conversation schema version two describes issue classification and does not itself authorize an execution profile.

Adaptive version-two integrated execution follows this order:

1. Read-only planning maps every acceptance ID to meaningful named existing or proposed checks and explains `coverage.mode`: `reuse` or `extend`. The current code-only profile maps criteria to Node checks and rejects browser obligations.
2. In `reuse`, the owner resolves existing named checks and freezes the complete baseline inventory with a distinct source/plan/criteria/contract-bound reuse receipt. No tests worker or new-test acceptance review runs. The final independent code reviewer must confirm coverage remains meaningful for the actual change.
3. In `extend`, add or repair only unapproved scoped checks. Controller-owned red proofs and independent acceptance review precede freezing. Draft rejection uses the existing cumulative acceptance budget. Existing checks remain protected.
4. Implement within scope and run selected named checks for early diagnostic feedback. A focused pass cannot authorize readiness, integration or publication.
5. Apply the candidate to the latest enrolled target and execute one fresh complete verifier there. Independently review that exact integrated source and evidence. Repair rejection within cumulative budgets, then repeat the necessary diagnostics, full integrated verification and review.
6. Advance the target only to the exact verified and approved tree. A moving target requires a new integrated proof; dirty checkouts and unsafe ownership block.
7. Run the durable whole-requirement acceptance job after all child merges. It may reference eligible unchanged integrated verification evidence. An exact sole-child combined approval may cover the original goal; otherwise obtain a fresh independent whole-goal review. Record every reused run and original timestamp.

Legacy version-one execution retains planning, tests, red proofs, acceptance review/freeze, full candidate verification, full integrated verification and final integrated code review. Its whole-requirement job continues fresh verification and review. Direct delivery-only execution in either version retains fresh complete candidate verification and independent code review. Maintenance retains separate owner admission and source review. Full gate commands, required identities, permissions and cumulative budgets are unchanged.

Owner receipts bind review purpose, source hash, canonical plan identity, acceptance identity, verification contract, and evidence path. Rejected reviews and earlier test generations retain separate evidence. Workers cannot approve themselves by writing a hash or claiming completion.

Initial acceptance runs controller-owned named Node proofs. A named assertion failure establishes missing behavior; an exact named pass records already-satisfied behavior for independent review. Import errors, setup errors, missing cases, skips and timeouts cannot authorize freezing. The current code-only profile rejects browser obligations before execution. Meaningful red proofs and independent coverage approval precede accepted test inventory freezing.

### Improve drafts inside the existing tests phase

The `tests` and `regression-tests` prompts include a short self-check based on observed acceptance rework. It adds no role, phase, gate or budget. Apply only relevant checks to the planned behavior:

| Risk in a draft | Stronger behavior proof |
| --- | --- |
| A removed tool leaves obsolete fixture paths, commands, report locations or named cases. | Inspect migrated references and run the affected setup and known-good baseline before approval; retain actual command/log/report evidence. |
| Fixture preparation fails before the behavior is observed. | Correct the unapproved fixture first; owner red proof must reach the intended named assertion. New behavior may still be red. |
| A fixture assumes an incidental count or file order. | Assert the actual required identities or boundary; use a count only when it is itself contractual. |
| Only matching records exist or raw fixture words satisfy the result assertion. | Include relevant excluded records and assert application-generated values separately from fixture source. |
| A rejection message alone appears to prove safety. | Assert the rejected operation does not mutate state and the relevant valid boundary is accepted. |

The same acceptance reviewer inspects focused readiness results and owner assertion proofs before freezing. Consolidate corrections while drafts remain unapproved. This focused work does not add another role, approval stage or full verifier.
Baseline and accepted bytes remain protected. Before approval, the initial tests role may revise only its current unapproved appended regions or new scoped files; the regression-tests role may revise only its own new scoped files. Keep planned and reported check identities aligned rather than accumulating unmapped replacement scenarios after feedback. Record a known sandbox startup `EPERM` once, stop repeated denied process launches, and leave owner red proofs to the controller.

The [assertion observation guidance](assertion-observations.md) also reaches tests, regression-tests and acceptance-review within their existing phases. Locate identity and current-state fields independently of expected values, assert their visible values separately, and check both incorrect-result false passes and equivalent-presentation false failures. Scoped prose containment remains valid. The former requirement candidate's identity/state revisions are now historical delivered contracts. Apply [risk-proportionate observation guidance](assertion-observations.md): an exact positive value needs no logically redundant opposite-state assertion, and speculative presentation preferences are nonblocking. Existing accepted checks and cumulative budgets remain protected.

Adapter regressions verify that the authoring and acceptance-review roles receive their applicable guidance with existing response schemas and permissions. They prove prompt delivery, not guaranteed model output quality. Controller-owned red proofs, independent acceptance review, frozen checks, complete verification and final source review remain authoritative. Observe future draft rejection and repair evidence before claiming reduced rework.

Acceptance and final code reviews may correct a malformed structured response once within the same phase. The correction shares the original phase deadline, attempt number, source, plan and evidence. Both responses count toward active execution time; no planning or tests generation restarts and no budget resets. The controller retains the original response and validation error in `phase-*/contract-error.json`. A valid rejection follows the existing repair path. Failed or timed-out processes are not format errors. Read-only source checks run after every response or invocation failure, before format correction or approval. An approved review requires an empty blocking-findings array; the controller never deletes findings to manufacture approval.

## Retry without losing accepted work

Checkpoints live in the run evidence directory, outside disposable worktrees. They include a reconstructable binary patch, added and deleted source, baseline identities, plan, accepted test hashes, review, and named red-proof hashes. A retry receives a new run ID and preserves its predecessor. Ownership checks follow the full predecessor lineage and all earlier issue runs; repeated retry cannot hide an older live process.

The controller can reuse accepted planning/test evidence only when the goal, criteria, scope, budget, controls, original tests, dependency lock, runtime, active harness, and proof hashes match. It records every invalidation reason. Unapproved drafts remain evidence and cannot authorize implementation. Every restored draft gets fresh full verification and code review. Verified merge recovery runs before replay so a crash after integration cannot apply the change twice.

Delivery-only baseline reconstruction uses the recorded immutable `baselineTree`, which may contain original uncommitted modifications and new files absent from `baseCommit`. Restore that tree before applying `checkpoint.patch`, then validate the exact source and frozen test inventory. Keep the original baseline as the final patch/change-attribution boundary. Set `resume.reused` only after reconstruction and enforcement succeed; a failed restoration remains false and blocks without consuming a new implementation attempt. Clean-target queue admission, cumulative budgets and fresh verification/review remain unchanged.

Accepted checkpoints retain initial Node logs and machine reports, bound to independent acceptance receipts and approved test hashes. The compatibility browser lists remain empty. Missing, altered or orphaned Node proof metadata rejects reuse. Revised protected controls invalidate older checkpoints through environment identity. Restoration copies original proofs without manufacturing a new execution; fresh complete verification and final review remain mandatory.

Acceptance attempts, implementation attempts, and active execution time are cumulative per issue. Waiting between completed runs is not charged. A hard crash conservatively spends its active phase reservation. Retry cannot silently increase budgets or alter criteria. Exhaustion requires a separate owner decision.

Owned subprocess receipts include all discovered process groups and their cleanup state. Recovery refuses unsettled groups and retains unsafe workspaces for owner inspection. Stale execution lease reclamation is serialized. A crash while holding the short admission guard requires explicit inspection of that guard; automatic concurrent guard reclamation is deliberately unavailable. Inspect exact recorded PIDs and identities before cleanup, never process names.

## Classify verification failures conservatively

Retain the failed summary, actual reports and process ownership receipts before choosing recovery. Product assertion failures use implementation repair; invalid test preparation or contract assertions require the reviewed test-maintenance path. Unknown timeouts and error prose cannot prove an infrastructure cause.

Only positive structured spawn diagnostics for `EAGAIN` or `ENFILE`, a matching failed gate and settled cleanup can authorize one same-source verification retry. Its separate infrastructure counter is cumulative across the issue lineage, active time is still charged, and it does not consume a new implementation attempt or reset any budget. A second occurrence, changed source/controls or unsafe ownership blocks ordinary recovery. Preserve both verifier executions and their diagnosis; a later pass never erases the original failure.

Adaptive focused behavior failures receive independent `focused-failure-triage` disposition through the existing acceptance-review role before further product repair. The controller checkpoints the exact failed source and hashed report/log copies before review. Invalid or interrupted review leaves the hold in place; matching checkpoint recovery must resolve it before consuming another implementation attempt. Rejection or uncertainty routes to owner maintenance without changing accepted assertions. Approval permits ordinary repair only and is neither delivery approval nor a passing verification result. The normal passing route adds no review call. See the [owner workflow](owner-workflow.md#diagnose-a-failed-focused-check) for evidence and continuation boundaries.

## Reuse integrated evidence without manufacturing execution

`integrated-verification-certificate.json` binds the actual integrated commit/source, executing engine/runtime, dependency installation, controls, effective required-check contract, complete four-gate report and underlying Node reports to a source-bound approved code-review receipt. The latest merged child's integration commit must equal the current target. Every current child must have owned merge evidence. Missing or changed evidence, identity or environment falls back to fresh complete verification.

A single-child requirement may reuse review only when the receipt purpose explicitly includes both integrated code and the original whole goal, and exact requirement ID, goal, child identity and acceptance match. Multiple-child requirements and changed goals require fresh independent whole-goal review. Verification reuse alone does not approve a business goal.

The whole-goal run retains exact original report bytes and explicit `verification-reuse.json` provenance, including original run ID and start/completion times. It never invents a newly executed pass. GitHub exact-head CI, confirmed PR merge and clean target synchronization remain required.

## Read a delivery

The issue report presents the goal, result, changed files, decisions, named behavior checks, verification counts, review outcome, merge commit, execution timeline, cumulative budget, predecessor, and reuse decision. Legacy reports remain readable without the new optional fields.

The controller's final Result and current limitations reflect its outcome and actual failure reason. Optional `workerObservations` preserves each implementation summary in an explicitly historical UI/Markdown section, alongside the original worker JSON. Sandbox-only or pending worker observations are not current blockers after owner verification passes. If later queue admission or recovery changes a proposal to Blocked, its Result must also show the owner blocker. Existing historical evidence is retained as recorded rather than rewritten.

Optional execution and efficiency fields report the chosen route, actual agent/test-authoring invocations, verification executions/retries/reuses and measured phase durations. Each planner process counts separately, including structured-response correction; custom adapters without execution notifications count once per call. Reused verification contributes no fresh execution time; original timestamps stay in provenance. Deterministic adapters measure orchestration, not real model latency.

For workflow improvement, retain `state.json`, `task.json`, `plan.json`, review receipts, checkpoint manifests/patches, machine reports, and phase logs. The evidence manifest provides file sizes and hashes. Browser checking is retired; historical reports remain audit evidence. Read the compact delivery first and open detailed evidence only for a concrete question.

A final reviewer that ignores cancellation must keep its exact integration worktree through both cleanup paths. The owner records the retained workspace and safety reason, and queue cleanup also preserves the candidate worktree. This rule is covered by real controller and queue interruption regressions; settled successful and rejected reviewers still clean up normally. Requirement-level review can block an otherwise passing delivery and create a separately reviewed corrective issue without changing the frozen original requirement membership or acceptance criteria.

Process-group inspection treats only `ESRCH` as confirmed absence. `EPERM` and other probe errors remain unsafe and are retried within the existing cleanup window. A persistent error returns a structured failure with `settled: false`; it cannot escape from an exit callback or prevent the ownership receipt from being finalized. The result and receipt use the same final observation. Receipts retain bounded diagnostic probe errors even when a later probe confirms absence. On Darwin, a zombie-only group can produce `EPERM` ([Apple XNU signal implementation](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_sig.c#L1612-L1621)); this possibility does not authorize treating `EPERM` as dead or weakening the positive-PID cancellation assertions.

## Close a confirmed coverage gap

A final independent code reviewer sets `needsRegression: true` only when a blocking, reproducible product defect lacks deterministic coverage. The finding states the trigger and expected behavior. Existing failing checks use ordinary repair. Speculative improvements and new business goals do not enter this branch.

The controller sends that finding to the existing tests role as `regression-tests`. It may create new scoped Node test files only. Every existing file, including accepted tests and the defective implementation, remains unchanged. The response lists exact new file names and test titles. No defect registry, additional issue hierarchy, or new service is required.

The controller runs each named new check against the reviewed defective candidate. A passing check, missing case, import failure, setup failure, skip, or timeout cannot establish a regression red proof. Node proofs use the trusted reporter and disposable server/database when an HTTP outcome is required. An independent acceptance reviewer reads the finding, checks, and actual red proofs. Rejected drafts can be revised within the existing cumulative acceptance budget. Only approved checks are frozen and added to the effective verification contract. The repair worker then fixes the product while all accepted checks remain immutable.

Legacy candidate verification, mandatory fresh integrated verification, final independent code review, verified local merge, and whole-requirement acceptance retain the responsibilities of the selected profile. An integrated review of a newer target cannot authorize red proofs against a different worker snapshot: the controller blocks for owner rebase when the reviewed source differs. Scope and criteria never expand through a regression request.

Before regression generation, a checkpoint retains the rejected reviewed candidate and pending request. Unapproved test drafts remain evidence and are never promoted by interruption recovery. Retry regenerates those drafts and repeats red proofs and independent acceptance review. After approval, checkpoints retain the new check hashes, red logs and machine reports, and source-bound coverage receipt; retry restores these checks frozen and runs fresh complete verification and code review. Orphan regression proof files or review receipts reject reuse, so missing pending or accepted regression metadata cannot silently authorize repair. Acceptance attempts, implementation attempts, elapsed execution time, and ownership lineage remain cumulative. Exhaustion still requires an explicit owner decision.

Delivery reports include the added behavior checks, coverage receipt, phase timing, and proof paths. New test files are discovered by the ordinary test commands after integration, so later tasks run the regression automatically. `acceptance/refresh-focus.spec.ts` is the permanent regression for issue opener retention and focus restoration during a job-triggered background refresh, covering success/failure and title/identifier entry controls.

The frozen contract includes the complete approved file inventory under `tests/` and `acceptance/`, including helpers. Implementation and repair cannot add test files after coverage approval. A reuse-only plan cannot extend that inventory. Only the initial extension tests phase or the independently reviewed `regression-tests` branch can extend it. Accepted checkpoints read the controller-owned `accepted-checks.json` inventory and verify exact file membership and hashes before writing a patch or manifest. Interrupted draft capture uses the same checkpoint gate; unreviewed files cannot become accepted through recovery. The approved inventory is itself a hashed checkpoint proof; loaded checkpoint metadata must match it before reuse. Restoration also checks exact membership. A rejected capture retains the last valid checkpoint and its proof bytes.

## Publish accepted requirements

GitHub-enrolled requirements freeze their repository, remote, workflow, branch, base and accepted head. Feature children integrate into that requirement branch; owner maintenance derives the same target. Whole-goal verification remains mandatory and binds publication to the current owned report and exact committed source. A local acceptance or child merge cannot establish GitHub delivery. Cross-requirement dependencies require the predecessor's confirmed publication; internal dependencies retain ordinary child merge readiness.

Publication uses bounded owner processes and persistent `requirement_publish` jobs, without another agent or service. Pending CI defers a poll; restart reconciles interrupted publication only. Lost create/merge responses reuse the reserved PR and stored CI identity. The publisher verifies the latest configured workflow, PR/head/base identity, all returned jobs/checks/statuses and strict required-check/admin protection before a SHA-conditioned merge. GitHub enforces the target race boundary. It records the confirmed remote merge and synchronizes the clean local target before requirement completion. `.github/` joins protected controls. Failed CI, changed identities and unresolved Git operations block without weakening gates, force-pushing, resetting budgets or silently publishing legacy requirements. See [GitHub delivery](github-delivery.md).

Whole-goal approval metadata and its successful run outcome commit in one SQLite transaction. Retry selects publication only for the current owned passed whole-goal run; partial or interrupted approval metadata returns to whole verification. Prior publication process ownership must settle before any further job uses the shared repository. Ambiguous Git push destinations are rejected before spawning push. Pending additional checks/statuses defer observation, while terminal failures block. The merged publication state is written only after confirmed remote merge and successful local synchronization.

## Owner maintenance admission and continuation

Use the [owner workflow](owner-workflow.md) commands instead of copied recovery loops. Create and enqueue the authorized maintenance issue before owner work. Completion performs read-only admission before Git/evidence and repeats the same eligibility within the transactional claim; it never silently enqueues or restarts work. Await focused and full checks, including owned-process cleanup, before editing the same source/tests/configuration or execution engine. Cancel and settle before editing if necessary; source/input drift invalidates proof rather than demonstrating a product defect. Independent complete test-inventory approval precedes implementation and frozen full verification. Verification edits create stale proof; they never authorize changed source. Explicit idempotent continuation grants extend the existing cumulative ledger without changing the canonical task, and the native queue claims only the selected issue with all normal guards. Preserve process lineage, original goal, all four code gates and final independent source review.
