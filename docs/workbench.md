# Autonomous development workbench

## Start and use

Run `npm run dev`. The supervisor starts the loopback API, Vite, and one queue worker. Production use is `npm run build` followed by `npm start`; that supervisor starts the built application and the same queue worker. `npm run worker -- --once` processes at most one runnable job when no other worker owns the database.

Open an issue title or its LOC identifier to inspect the same read-only diagnostics dialog. Issues is the primary workspace; status navigation, repository/status/label filters, search, sorting, creation and confirmed deletion remain available. The Workbench page and manual repository/requirement administration forms have been removed. Escape or Close dismisses diagnostics and returns focus to the opener.

Diagnostics retain issue identity, description, status, priority, labels, timestamps, repository, dependencies and acceptance conditions. Associated requirements retain their original goal and available conversation provenance: submission ID, plan hash, source kind, reference and summary. Standalone issues and missing provenance are identified explicitly. Verified child progress counts distinct issues with recorded owned merges. A Done status, duplicate runs, zero children or planning approval cannot establish delivery. Whole-goal verification requires all nonzero children merged and a passed run belonging to the latest completed requirement_verify job; newer unresolved attempts supersede older passes.

Repository enrollment and manual requirement creation/start remain available through the existing local APIs documented in [architecture](architecture.md). The application registers its own checkout as the first repository when it starts on a branch. The backend submission, ownership, queue, independent review and automatic integration controls are unchanged. A read-only agent proposes issues, defaults, acceptance conditions and dependencies; a fresh agent reviews coverage before implementation is released.

Codex conversations can instead submit an entire immutable plan through `npm run submit-plan -- <plan.json>`. The original requirement, source, issues, and dependency mapping appear in issue diagnostics. One independent `plan_review` job runs before any submitted issue can execute. The controller reuses the submitted decomposition and releases it only after coverage approval. See [conversation intake](conversation-intake.md) and the repo skill `.agents/skills/issue-tracker-submit/SKILL.md`.

The queue runs one job at a time across enrolled repositories. An issue waits for verified merge receipts for every dependency, including dependencies that belong to another requirement in the same repository. A manually selected Done status does not satisfy execution dependencies. Queued and running issues are frozen; automatically merged issues are immutable. Use a new follow-up issue for later changes.

Requirement membership is frozen after its first start. Only the owner-controlled decomposition transaction can create its initial children. Children cannot be added, removed, or moved into a requirement during final verification or after completion. A final admission transaction also requires merge evidence for every current child. Failed siblings and cross-requirement dependency failures keep the affected requirements Blocked; retries become available when their active work drains.

Standalone issues can also be started from their details. Choose a repository, acceptance conditions and optional dependency IDs when creating an issue; existing assignments can be managed through the guarded API. The UI uses the first enrolled repository by default. Existing records keep their values and receive a standalone assignment when the application initializes its first repository. This does not launch any work.

## Execution and automatic merge

Registered repositories currently use the lab's Node/Playwright verification profile: installed dependencies, `src/`, `tests/`, `acceptance/`, a package with lint/typecheck/test/build/test:e2e scripts, machine Node output, and `factory/verification-contract.json`. Other Git repositories can be tracked, but execution needs that profile. New stack profiles are separate harness changes.

Automatic execution starts from the exact target commit and requires a clean enrollment checkout. It does not include uncommitted edits or borrow a different branch's harness. Each issue gets an owned detached worktree, distinct ports, and a disposable database. Its frozen task snapshot records the approved goal and conditions. Ordinary implementation defaults are recorded by the planning agent.

The controller prepares or reuses behavior checks, proves useful red assertions, freezes reviewed checks, implements within scope, reads owner-run machine reports, and obtains independent agent review. A worker cannot weaken existing checks or change harness configuration. Issue workers are limited to application, tests, acceptance, and documentation paths. Harness improvements are separately reviewed changes to the control system.

Before merge, the owner applies the patch to the latest target in another disposable worktree. The combined result receives full verification and a fresh read-only review. The owner checks source identity throughout and records the exact Git tree and proposed commit before advancing the target. Local integration is fast-forward only. A target ref that moves during verification triggers a new integration attempt, up to three attempts. Conflicts, dirty checkouts, rejected reviews, failed checks, and exhausted budgets block completion.

Repository integration uses an exclusive `loop-integration.lock` file in its common Git directory with the owner's PID, run ID, and start time. A copy is retained as `integration-owner.json`. A database queue lock also prevents two worker processes from owning the same queue. After a crash, inspect the recorded owner and stop any surviving owned processes before removing that exact stale lock; do not remove a live lock. This is a cooperative local ownership protocol; unrelated tools must not edit enrolled checkouts or refs during integration. No external Git push is needed for local completion.

All child issues must have successful merge receipts before a whole-requirement verification job is queued. That job verifies the latest target and obtains a fresh review against the original business goal and all deliveries. Only then does the requirement become Done. Human sampling is optional and does not gate execution or completion.

## Records, reports, and evidence

SQLite schema version 3 adds repositories, requirements, issue assignments, persistent jobs, and run indexes. API and queue processes share transactional SQLite operations. Claims are atomic; only one job can be running. Job payloads are frozen snapshots. Dependency cycles, missing references, cross-repository dependencies, and duplicate active starts are rejected.

Schema version 4 adds immutable plan submissions, source metadata, canonical hashes, and local-key mappings. A repeated submission ID with the same canonical plan returns existing IDs and current state, never a new execution. Different content under that ID conflicts. Submitted issues are immutable even before coverage review; rejected or interrupted plans cannot bypass review through a direct issue start.

Each execution writes outside its candidate checkout to `.data/evidence/<run-id>/` beside the application database. Direct factory runs default to the repository's `.data/evidence/`. Every successful or blocked controller execution generates `delivery.json` and `delivery.md` from owner records. The report includes the goal, the implementation worker's result summary, defaults and reasons, changed files grouped by application/tests/harness/documentation, named planned behavior checks, real gate and case results, attempts, independent review, verified source hash, baseline, integration commit, limitations, and a hashed evidence manifest. The result summary is explanatory prose; readiness still comes from owner verification and review.

Issue diagnostics group owned issue executions and requirement decomposition, plan-review and whole-goal runs in one keyboard-accessible selector. Failed attempts remain inspectable after successful retries. Each selection shows its own run ID, timestamps, outcome, report and evidence. Current job/run reasons and current delivery limitations appear separately from historical selections, including blocked executions without a delivery report. Inactive assigned work retains guarded Start issue or Retry issue actions. Queued, running and merged work cannot be started twice. Loading, running without a report, terminal report unavailability and recoverable request failures are explained explicitly. Retry details and Retry report repeat failed reads.

Delivery reports expose recorded independent review approval/rejection, verification counts and named checks, changes, phases, recovery/checkpoint reuse, cumulative attempts, failed phase, verified source and integration commit. Missing reports or optional fields never establish review approval or a verified merge.

Expand Evidence and select a manifest artifact to preview logs, JSON, Markdown, diffs and supported text as escaped plain text. Previews accept at most 1,048,576 received bytes (1 MiB), including the exact boundary. Empty files, loading, errors and retry are explicit. Binary, unsupported and oversized files offer a download fallback. Switching artifact, run or issue, or closing the dialog aborts obsolete preview requests. Every manifest entry retains its unchanged download URL. The verified endpoint restricts downloads to owned manifest entries inside the run directory and checks their stored hash. Source worktrees, dependencies and the trusted verifier checkout are excluded. Diagnostics wrap long titles, provenance, errors and text at desktop and 390px widths. Logs, prompts, structured responses, red proofs, machine results, review receipts and patches remain available; trace ZIPs are retained only for failed browser tests.

`.runs/` holds verification and scratch artifacts. Clearing it does not remove application evidence. Keep `.data/` out of Git and back up the application database with its evidence directory. Reset replaces the backlog, repository registry, job history, and demo records; it refuses both a live API owner and a live queue owner. It leaves evidence files intact.

## Failure and recovery

Issue execution allows three implementation attempts, ten minutes per agent phase, and one hour total. This uses the existing task-contract maximum without changing acceptance criteria or verification budgets. Requirement planning/review phases retain their five-minute process budget and at most one protocol-repair attempt with separate retained logs. Each process has timeout and output budgets. Cancellation terminates only owned process groups.

An issue failure blocks queued dependents and marks its requirement Blocked. Issue diagnostics show the latest matching current job/run reasons; recovered failures remain in execution history. Queued work explains dependency waiting and lists prerequisite issue IDs. Use contextual Retry issue for inactive assigned work, or the existing requirement start API to retry an inactive blocked requirement after resolving its cause; already merged issues are preserved. Active and merged issues reject duplicate admission. Submitted plans still require independent planning review. A retry receives a new run ID and the latest matching blocked run's reason as diagnostic context, capped at 12,000 characters. This feedback does not change the immutable goal, criteria or review gates. Independent review failures and infrastructure limitations remain visible in reports.

Before implementation, rejected new behavior checks receive independent findings and can be revised within the task's attempt limit and total deadline. Original test bytes and implementation remain protected during these revisions. A fresh acceptance review must approve the checks before they are frozen; repeated rejection blocks the run. Numbered test and acceptance-review reports preserve each decision.

On startup, interrupted executions are blocked unless durable integration verification, review, tree, and commit receipts prove that their merge is already on the enrolled target. Proven merges are reconciled into the database instead of being repeated. Queue locks left by a crash require inspecting and stopping their recorded owner before removing them. This prototype does not promise hostile-worker isolation or automatic recovery of arbitrary detached processes.

The deterministic queue and integration tests prove orchestration using disposable Git repositories and real Node/Playwright reports. Browser acceptance exercises enrollment, requirement launch, completed issue reports, evidence download, ownership, and dependency rejection through the actual application. Those deterministic worker adapters do not measure model quality; live Codex pilots provide separate evidence.

## Maintenance delivery

Version-two plans can classify separate acceptance-contract and harness issues. Their `maintenance` jobs wait for owner evidence; ordinary workers cannot claim them. Feature dependents wait for recorded maintenance merges. Use the owner recorder described in factory/README.md after full verification, independent review, and actual local integration. Human audit remains optional. Classification never grants the feature executor control-plane write permission.

Retries retain accepted checkpoints and bounded budgets across run IDs. Open the earlier and current delivery evidence to see the predecessor, reuse decision, failed phase, and checkpoint proof hashes. A changed goal, acceptance contract, original test, harness, dependency lock, or runtime invalidates reuse. Infrastructure/process ownership blockers require cleanup of the verified owner before retry; retry never relaxes tests or expands execution authority.

Delivery reports now include an execution timeline, review purposes, cumulative budget, failed phase/category, and checkpoint reuse decision. The full review and recovery contract is in `docs/harness-reliability.md`. The new fields are optional so historical reports remain readable.
