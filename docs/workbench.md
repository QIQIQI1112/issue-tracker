# Autonomous development workbench

## Start and use

Run `npm run dev`. The supervisor starts the loopback API, Vite, and one queue worker. Production use is `npm run build` followed by `npm start`; that supervisor starts the built application and the same queue worker. `npm run worker -- --once` processes at most one runnable job when no other worker owns the database.

Select a repository, then Issues or Repo harness. All repositories shows issues across the registry, including unassigned records. Open an issue title or its LOC identifier to inspect the read-only diagnostics dialog. Repository selection, status/label filters, search and sorting remain available. Creation, editing, deletion and execution admission use the conversation CLI or guarded local APIs; the browser has no mutation forms, execution controls or Workbench page. Escape or Close dismisses diagnostics and returns focus to the opener.

Diagnostics retain issue identity, description, status, priority, labels, timestamps, repository, dependencies and acceptance conditions. Associated requirements retain their original goal and available conversation provenance: submission ID, plan hash, source kind, reference and summary. Standalone issues and missing provenance are identified explicitly. Verified child progress counts distinct issues with recorded owned merges. A Done status, duplicate runs, zero children or planning approval cannot establish delivery. Whole-goal verification requires all nonzero children merged and a passed run belonging to the latest completed requirement_verify job; newer unresolved attempts supersede older passes.

Repository enrollment and manual requirement creation/start remain available through the existing local APIs documented in [architecture](architecture.md). The application registers its own checkout as the first repository when it starts on a branch. The backend submission, ownership, queue, independent review and automatic integration controls are unchanged. A read-only agent proposes issues, defaults, acceptance conditions and dependencies; a fresh agent reviews the submitted plan before implementation is released. Small cohesive requirements default to one issue. Split only for independently useful delivery, real dependencies or owner-maintenance boundaries.

Codex conversations can instead submit an entire immutable plan through `npm run submit-plan -- <plan.json>`. The original requirement, source, issues, and dependency mapping appear in issue diagnostics. One independent `plan_review` job runs before any submitted issue can execute. The controller reuses the submitted decomposition and releases it only after coverage approval. See [conversation intake](conversation-intake.md) and the repo skill `.agents/skills/issue-tracker-submit/SKILL.md`.

The queue runs one job at a time across enrolled repositories. An issue waits for verified merge receipts for every dependency, including dependencies that belong to another requirement in the same repository. A manually selected Done status does not satisfy execution dependencies. Queued and running issues are frozen; automatically merged issues are immutable. Use a new follow-up issue for later changes.

Requirement membership is frozen after its first start. Only the owner-controlled decomposition transaction can create its initial children. Children cannot be added, removed, or moved into a requirement during final verification or after completion. A final admission transaction also requires merge evidence for every current child. Failed siblings and cross-requirement dependency failures keep the affected requirements Blocked; retries become available when their active work drains.

Standalone issues can be created and started through the guarded API. Supply a repository, acceptance conditions and optional dependency IDs; existing assignments can also be managed through the API. An API-created issue without an assignment receives the first enrolled repository when available. Existing unassigned records keep their values and receive a standalone assignment when the application initializes its first repository. This does not launch work.

## Execution and automatic merge

Registered repositories currently use the lab's code-only verification profile: installed dependencies, `src/`, `tests/`, a package with lint/typecheck/test/build scripts, complete machine Node output, and a schema-version-two `factory/verification-contract.json` with named Node requirements and no browser obligations. Other Git repositories can be tracked, but execution needs that profile. New stack profiles are separate harness changes.

Automatic execution starts from the exact target commit and requires a clean enrollment checkout. It does not include uncommitted edits or borrow a different branch's harness. Each issue gets an owned detached worktree, distinct ports, and a disposable database. Its frozen task snapshot records the approved goal and conditions. Ordinary implementation defaults are recorded by the planning agent.

The controller selects its execution profile from the protected repository policy. Missing `factory/execution-policy.json` keeps `legacy-v1`; `{ "schemaVersion": 1, "mode": "adaptive-v2" }` enables adaptive version-two tasks and malformed policy blocks. Adaptive plans either reuse named existing coverage with an owner baseline receipt or extend coverage through test authoring, owner red proofs, independent acceptance review and freezing. Every acceptance condition needs meaningful named Node coverage; browser obligations are rejected under the current profile. Development runs related named checks for early feedback; final independent review confirms coverage of the actual change. A worker cannot weaken existing checks or change harness configuration. Issue workers are limited to application, tests, acceptance, and documentation paths. Harness improvements are separately reviewed changes to the control system.

Before merge, the owner applies the patch to the latest target in another disposable worktree. The combined result receives full verification and a fresh read-only review. The owner checks source identity throughout and records the exact Git tree and proposed commit before advancing the target. Local integration is fast-forward only. A target ref that moves during verification triggers a new integration attempt, up to three attempts. Conflicts, dirty checkouts, rejected reviews, failed checks, and exhausted budgets block completion.

Repository integration uses an exclusive `loop-integration.lock` file in its common Git directory with the owner's PID, run ID, and start time. A copy is retained as `integration-owner.json`. A database queue lock also prevents two worker processes from owning the same queue. After a crash, inspect the recorded owner and stop any surviving owned processes before removing that exact stale lock; do not remove a live lock. This is a cooperative local ownership protocol; unrelated tools must not edit enrolled checkouts or refs during integration. No external Git push is needed for local completion.

All child issues must have successful merge receipts before a whole-requirement verification job is queued. That job proves the original goal against the latest target and all deliveries. Adaptive execution may reuse exact eligible integrated verification evidence and, for a sole child only, an explicitly combined approval bound to the original requirement ID and goal. Missing or changed source, runtime, dependencies, controls, contracts or actual report/review bytes force fresh verification; multiple-child or changed-goal work requires fresh whole-goal review. Legacy execution keeps fresh whole verification and review. This completes a local-only requirement. A GitHub-enrolled requirement additionally needs exact-head CI, confirmed PR merge and clean local synchronization before becoming Done. Human sampling is optional and does not gate execution or completion.

## Records, reports, and evidence

SQLite schema version 3 adds repositories, requirements, issue assignments, persistent jobs, and run indexes. API and queue processes share transactional SQLite operations. Claims are atomic; only one job can be running. Job payloads are frozen snapshots. Dependency cycles, missing references, cross-repository dependencies, and duplicate active starts are rejected.

Schema version 4 adds immutable plan submissions, source metadata, canonical hashes, and local-key mappings. A repeated submission ID with the same canonical plan returns existing IDs and current state, never a new execution. Different content under that ID conflicts. Submitted issues are immutable even before coverage review; rejected or interrupted plans cannot bypass review through a direct issue start. Version 5 adds maintenance change classifications; version 6 adds GitHub enrollment/publication metadata and deferred job availability. `src/storage.ts` declares the current supported version.

Each execution writes outside its candidate checkout to `.data/evidence/<run-id>/` beside the application database. Direct factory runs default to the repository's `.data/evidence/`. Every successful or blocked controller execution generates `delivery.json` and `delivery.md` from owner records. The report includes the goal, final owner outcome, defaults and reasons, changed files grouped by application/tests/harness/documentation, named planned behavior checks, real gate and case results, attempts, independent review, verified source hash, baseline, integration commit, current blockers, and a hashed evidence manifest. Optional `workerObservations` retains implementation summaries as historical context in the UI and Markdown, separate from the final Result and current limitations. Original worker JSON remains evidence. Readiness comes from owner verification and review, never from worker prose. Historical reports retain their original stored text and remain readable.

Issue diagnostics group owned issue executions and requirement decomposition, plan-review, whole-goal and GitHub publication runs in one keyboard-accessible selector. Failed attempts remain inspectable after successful retries. Each selection shows its own run ID, timestamps, outcome, report and evidence. Current job/run reasons and current delivery limitations appear separately from historical selections, including blocked executions without a delivery report. Guarded execution starts/retries are API operations; queued, running and merged work cannot be started twice. Loading, running without a report, terminal report unavailability and recoverable request failures are explained explicitly. Retry details and Retry report repeat failed reads.

Delivery reports expose recorded independent review approval/rejection, verification counts and named checks, changes, phases, recovery/checkpoint reuse, cumulative attempts, failed phase, verified source and integration commit. Optional execution/efficiency fields record route, actual agent and test-authoring calls, verification executions/retries/reuses, elapsed time and measured phase durations. `verification-reuse.json` points to the original certificate and timestamps; exact retained reports do not imply a new test execution. Compact role context indexes preserve full feedback and owner evidence references for targeted inspection. Missing reports or optional fields never establish review approval or a verified merge.

Expand Evidence and select a manifest artifact to preview logs, JSON, Markdown, diffs and supported text as escaped plain text. Previews accept at most 1,048,576 received bytes (1 MiB), including the exact boundary. Empty files, loading, errors and retry are explicit. Binary, unsupported and oversized files offer a download fallback. Switching artifact, run or issue, or closing the dialog aborts obsolete preview requests. Every manifest entry retains its unchanged download URL. The verified endpoint restricts downloads to owned manifest entries inside the run directory and checks their stored hash. Source worktrees, dependencies and the trusted verifier checkout are excluded. Diagnostics wrap long titles, provenance, errors and text at desktop and 390px widths. Logs, prompts, structured responses, red proofs, machine results, review receipts and patches remain available; historical browser artifacts remain readable, but no new browser runs or traces are produced.

`.runs/` holds verification and scratch artifacts. Clearing it does not remove application evidence. Keep `.data/` out of Git and back up the application database with its evidence directory. Reset replaces the backlog, repository registry, job history, and demo records; it refuses both a live API owner and a live queue owner. It leaves evidence files intact.

Use the original regular database file path. Database-file symlinks and hard links are unsupported and are rejected before API/queue ownership, storage, reset, doctor and conversation intake. New nested paths and directory symlinks keep their existing behavior and resolved-path identity. Do not replace a database path or add file aliases while it is owned.

## Issue lifecycle

Open represents unstarted work. In progress follows an execution claim. Blocked represents failed work requiring attention, including interrupted recovery and blocked dependency cascades. A retry retains the original failure, lineage and cumulative budgets; claiming it changes the issue to In progress. Done retains its existing verified-delivery rules. Closed records an explicit abandonment or supersession and never establishes successful delivery.

Agents close inactive work through `POST /api/issues/:id/close` with `{ "reason": "Replaced by the verified follow-up.", "supersededBy": 22 }`. The reason is trimmed and must contain 1–2000 characters; `supersededBy` is optional and must identify another existing issue in the same repository without creating a replacement cycle. Unknown fields and client-supplied closure times are rejected. Use the existing pinned `X-Issue-Tracker-Target` identity and loopback/origin safeguards. Success returns the issue with server-owned `closure: { reason, closedAt, supersededBy? }`; missing issues return 404, invalid input 400, and conflicting lifecycle operations 409. Identical repeated close requests return the same record and timestamp.

The status selector defaults to All statuses and offers Open, In progress, Blocked, Closed and Done independently. It combines with repository, title/description search and label filters. Closed diagnostics show the reason as escaped text, the recorded closure time and the replacement issue ID/title from the complete issue collection, even when filters exclude that replacement. Missing replacements say “No replacement issue recorded.” An unavailable title retains the replacement ID and an explicit explanation. Closure context is separate from execution outcomes: original failed runs, selected reports, evidence, current failure reasons and current limitations remain inspectable. The website sends only inspection reads and has no lifecycle or execution controls.

### Pinned agent close procedure

Use the owner launch receipt to obtain the expected instance ID, resolved regular database path and assigned loopback API URL. Do not adopt an identity discovered from an unexpected server. Read `/api/health` and compare its `instanceId` and `databasePath` with that receipt before each mutation. Encode the expected pair as `encodeURIComponent(JSON.stringify([instanceId, databasePath]))` for `X-Issue-Tracker-Target`. A stale, malformed or mismatched supplied pin returns 409 before any write; an untrusted host or origin returns 403. Keep the pin on the close request even after a successful health check so a replaced server cannot receive the operation.

Read `/api/issues/:id`, the replacement's detail when present, and `/api/workbench` before closing. Confirm the intended repository and immutable requirement, inactive original work and the authorized replacement. Send only the reason and optional numeric `supersededBy`; never send a timestamp or change the ordinary status field to Closed. For example, after validating the owner identity and setting `PINNED_API_URL` and `PINNED_TARGET` from that receipt:

```sh
curl --fail-with-body --silent --show-error \
  -X POST "$PINNED_API_URL/api/issues/20/close" \
  -H "X-Issue-Tracker-Target: $PINNED_TARGET" \
  -H 'Content-Type: application/json' \
  --data-binary @close-request.json
```

The reviewed `close-request.json` must contain the durable owner reason and `"supersededBy": 22` for the authorized issue20 operation. Store the exact request and HTTP response/status with the evidence. A successful response is 200 with `{ "issue": ... }`. Repeating the same trimmed reason and replacement returns the original closure and timestamp; changing either after closure conflicts with 409. After a lost response, inspect the pinned target and original issue before replaying the identical request. Do not retry by starting execution, replaying a submission or editing the immutable plan. Read the issue and workbench again after success and inspect its retained diagnostics.

### Post-publication issue20 owner acceptance

This operation belongs to the conversation owner after confirmed requirement9 GitHub PR merge, exact-head CI and safe activation of the verified checkout. Child integration and isolated fixture tests do not authorize the implementation worker to operate on issue20 and cannot prove this acceptance. Retain the owner receipt under `.data/evidence/issue-lifecycle-20261020/` with:

1. The publication/CI identities, activated source commit, settled prior queue ownership and expected API instance/database identity. Keep the queue idle while capturing and comparing evidence so unrelated work cannot change the snapshots.
2. Before snapshots of issue20, issue22, requirement4, the original immutable submission/plan and hash, all original jobs/runs and lineage, consumed attempts and elapsed budgets. Preserve the original report/log/evidence files and their byte hashes, including delivery budget fields and report bytes rather than regenerated renderings.
3. The reviewed durable reason, exact pinned request, response/status and any identical replay. The request closes issue20 with `supersededBy: 22`; it does not start or retry any work.
4. After readback proving issue20 is Closed with that reason, server timestamp and replacement22; issue22 remains Done; requirement4 remains Blocked. Compare every retained plan/job/run/report/log/evidence/budget snapshot and require equality. Only issue20's lifecycle status, closure metadata and update timestamp should change.
5. Historical owner inspection of issue20's closure context and its original failed history, reports and logs, with the original requirement still unverified. Browser execution is retired in the current profile. Record exact evidence paths and any mismatch; do not claim owner acceptance until the comparisons pass.

Closing a submitted issue is a dedicated lifecycle operation, not a plan edit. Original goals, descriptions, acceptance, dependencies, submission hashes, failed jobs/runs/reports and budgets remain intact. Queued/running or merged work cannot close. Closed issues cannot restart, edit, move or delete; their referenced replacements cannot be removed or moved to another repository. A closed predecessor cannot satisfy dependencies through its replacement, and a requirement containing a closed child cannot restart or become Done through that closure. Follow-up work uses its own immutable plan. The browser remains an inspection surface with no closure button.

The version-seven migration preserves existing identities, assignments, foreign keys, history, publication metadata and the issue ID high-water mark. A legacy inactive issue with a latest blocked job and no running or merged run becomes Blocked without rewriting its original evidence. Existing manual Open/In progress/Done states and active work remain unchanged. The approved one-assertion activation is recorded in [the lifecycle contract](issue-lifecycle-contract.md).

Owner maintenance controls must be verified, independently approved and integrated before activation. When a requirement branch contains revised protected controls, keep the queue idle during owner handoff and load that verified checkout before dependent jobs; the workspace baseline copies its current protected source. Record the exact checkout/source, settle the previous owned queue, and restart only its replacement. Preserve the reserved requirement branch and GitHub completion gates.

## Failure and recovery

Issue execution allows three implementation attempts, ten minutes per agent phase, and one hour total. This uses the existing task-contract maximum without changing acceptance criteria or verification budgets. Requirement planning/review phases retain their five-minute process budget and at most one protocol-repair attempt with separate retained logs. Each process has timeout and output budgets. Cancellation terminates only owned process groups.

An issue failure marks the issue and queued dependents Blocked and marks its requirement Blocked. Issue diagnostics show the latest matching current job/run reasons; recovered failures remain in execution history. Queued work explains dependency waiting and lists prerequisite issue IDs. Use the guarded issue or requirement start API to retry inactive blocked work after resolving its cause; already merged issues are preserved. Active and merged issues reject duplicate admission; closed issues reject all restart admission. Submitted plans still require independent planning review. A retry receives a new run ID, the latest matching blocked run's complete reason and evidence path as diagnostic context; large role inputs remain in indexed retained files. This feedback does not change the immutable goal, criteria or review gates. Independent review failures and infrastructure limitations remain in the relevant current or historical evidence.

For a coverage extension, rejected new behavior checks receive independent findings and can be revised within the task's attempt limit and total deadline. Original test bytes and implementation remain protected during these revisions. Fresh owner red proofs precede independent acceptance review and freezing; repeated rejection blocks the run. Numbered test and acceptance-review reports preserve each decision.

A confirmed structured spawn resource failure (`EAGAIN` or `ENFILE`) with a matching failed gate and settled ownership may use one same-source verifier retry from the persistent issue budget ledger. It retains the original failure, charges active time, and does not consume another code attempt. Product/test-contract failures, unknown timeouts and prose cannot authorize that retry. The counter and ownership lineage survive restarts; controls or source changes invalidate recovery eligibility.

On startup, interrupted issue executions are blocked unless durable integration verification, review, tree, and commit receipts prove that their merge is already on the enrolled target. Proven merges are reconciled into the database instead of being repeated. Interrupted GitHub publication observations are reconciled through their persistent publication identity after ownership settles. Execution-lease reclamation is serialized and requires the recorded PID to be absent; an admission guard left by a crash requires explicit owner inspection. Never remove a live lock. This prototype does not promise hostile-worker isolation or automatic recovery of arbitrary detached processes.

The deterministic queue and integration tests prove orchestration using disposable Git repositories and real named Node reports. Node/API checks retain enrollment, requirement launch, completed issue reports, evidence download, ownership and dependency rejection; browser rendering and interaction are outside the current profile. Those deterministic worker adapters do not measure model quality; live Codex pilots provide separate evidence.

## Maintenance delivery

Version-two plans can classify separate acceptance-contract and harness issues. Their `maintenance` jobs wait for owner evidence; ordinary workers cannot claim them. Feature dependents wait for recorded maintenance merges. Use the owner recorder described in factory/README.md after full verification, independent review, and actual local integration. Human audit remains optional. Classification never grants the feature executor control-plane write permission.

Retries retain accepted checkpoints and bounded budgets across run IDs. Open the earlier and current delivery evidence to see the predecessor, reuse decision, failed phase, and checkpoint proof hashes. A changed goal, acceptance contract, original test, harness, dependency lock, or runtime invalidates reuse. Infrastructure/process ownership blockers require cleanup of the verified owner before retry; retry never relaxes tests or expands execution authority.

Direct delivery-only retries reconstruct the original immutable baseline tree before applying the candidate delta. This preserves original uncommitted files and excludes unchanged initial user work from task changes. Successful source and frozen-inventory validation precedes a true reuse decision. The ordinary queue still requires a clean enrollment checkout.

Delivery reports now include an execution timeline, review purposes, cumulative budget, failed phase/category, and checkpoint reuse decision. The full review and recovery contract is in `docs/harness-reliability.md`. The new fields are optional so historical reports remain readable.

## GitHub requirement publication

An explicitly GitHub-enrolled repository snapshots publication settings for each new requirement. Child integration advances a dedicated requirement branch; whole-goal acceptance queues publication rather than completing delivery. The persistent serial publisher creates or reconciles one PR, admits only exact-head CI under strict GitHub protection, confirms the remote merge and records the result before completion. Issue diagnostics expose its branch, PR, CI, merge SHA and blockers. See [GitHub delivery](github-delivery.md) for enrollment, the unchanged local-only and standalone workflows, polling, and recovery.
