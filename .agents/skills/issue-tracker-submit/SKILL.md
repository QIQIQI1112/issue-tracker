# Submit a conversation requirement

Keep the user in the conversation. Capture the business goal, necessary constraints, ordinary defaults with reasons, and independently verifiable issues with dependencies. Preserve the original goal for whole-requirement acceptance. Prefer one issue for a small cohesive change; split only for independently meaningful behavior, real dependencies or separate maintenance ownership. Reuse equivalent coverage and add tests only for actual gaps; use the current code-only profile with named Node coverage; browserChecks must be []. Inspect equivalent functionality and select one reasonable uniform shared implementation standard before checking or implementing it. Record that standard and its reason among the plan defaults. Read [the submission contract](../../../docs/conversation-intake.md) for the JSON format and commands.

Plan only capabilities required by the current goal, an actual caller or an existing documented contract. Apply minimum necessary implementation to product code, tests and fixtures; omit unused optional APIs, states, modes and extension points for hypothetical future needs. Preserve current correctness, validation, error handling, accessibility, security and accepted quality gates. Prefer meaningful existing coverage and minimal data/boundary fixtures; do not propose new or expanded framework/browser reimplementations or private framework API use for tests. Existing planning and review roles enforce these rules using current defaults and summaries, without another stage or report schema. Keep a scoped cleanup focused and state any retained fixture limitation.

Preserve durable shared component, typography and semantic-token standards, functional layout relationships, accessibility and meaningful behavioral acceptance. For future acceptance, do not add permanent exact-value pixel or prose assertions for ordinary local dimensions, spacing, radii, shadows, transition timings or documentation wording unless the owner explicitly establishes a durable exact-value contract. This guidance preserves frozen tests, role separation, process ownership, independent review, all four verifier/CI gates and original attempt, timeout and retry budgets.

Locate the platform checkout and running API. From that checkout, run `npm run submit-plan -- --list`. For a nondefault instance, supply `--url` and `--database`. Choose the enrolled repository matching the user's intended target. Never infer a repository ID from its position or register a different target without authorization.

Ask about unresolved business choices only when necessary. When the user authorizes execution, create one complete version-one plan under `.runs/submissions/`. Generate a UUID submissionId once and persist it before any request. Use the actual conversation ID or a stable local conversation reference, with a concise agreed-goal summary. Do not copy the entire chat. Use lowercase issue keys and key-based dependencies; make the graph acyclic. Use English harness records while preserving requested product language and behavior.

Validate offline with `npm run submit-plan -- <plan.json> --validate`, then submit with `npm run submit-plan -- <plan.json>`. Submission automatically queues independent coverage review. Report the returned Requirement and issue IDs, receipt path, and current status. A queued receipt establishes submission, not verified delivery.

The existing queue owns implementation, verification, independent review, and local integration. Do not develop the same submitted issues in the conversation checkout or start a competing executor. The controller chooses protected scope, budgets, and verification commands; the submitted plan cannot override them.

If a response is lost, query `npm run submit-plan -- --status <submissionId>` or retry the exact saved plan. A retry with the same ID and content returns the existing work. Changed content needs a new submission ID. A replay never restarts failed work. Inspect a Blocked report before requesting a retry; revised business work is a new immutable plan.

Retrieve status with `--status` and inspect the returned run report URLs or retained receipt. Claim Done only when the platform records whole-requirement completion after verified child merges and original-goal acceptance. For explicitly GitHub-enrolled requirements, child integration occurs on a reserved requirement branch and completion additionally requires the controller to confirm the GitHub PR merge after exact-head CI. Read publication state and PR/CI/merge evidence; local acceptance alone is insufficient. Local-only repositories retain local completion. See `docs/github-delivery.md`.

Use version-two plans when classifying maintenance: keep additive business checks with the feature; create separate `acceptance_contract` or `harness` issues for detector and control changes, with explicit dependencies. Change kinds are descriptive, never scope or approval. Maintenance jobs use the separately verified owner workflow and cannot run through the feature executor. Preserve version-one plan identities when replaying old submissions. Do not claim maintenance delivery until the owner records real verification, independent source review, and target integration evidence.
